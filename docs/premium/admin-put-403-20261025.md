# Admin purchase settings PUT 403 — 2026-10-25

## Confirmed cause

The failing operation is `PUT /admin/api/premium-purchase` (the GET of the same
resource succeeds with a valid admin session). Application-wide Ktor CORS rejected
the PUT **before** the admin route's session/CSRF checks. This is not a missing
frontend CSRF header or a purchase URL validation failure.

Production terminates HTTPS at Caddy and forwards HTTP to Ktor 3.5.2. Browser
Origin is `https://api.spdapp.shop`; Ktor's connection origin is HTTP. The CORS
same-origin shortcut therefore does not apply. Its configured/default method set
permits GET/HEAD/POST, not PUT, and its rejection is an empty 403. Local tests had
matching HTTP request/Origin and inadvertently bypassed that method check.

## Read-only production evidence

- Public PUT with the correct HTTPS Origin: 403, **zero response bytes**, no JSON
  content type. No production session or CSRF token was obtained or printed.
- Direct `127.0.0.1:8080` Ktor PUT with the production Host, HTTPS Origin and
  `X-Forwarded-Proto: https`: the identical empty 403, bypassing Caddy.
- PUT without Origin: structured `403 ORIGIN_INVALID`, showing the route's
  separate Origin guard remains active when CORS does not intercept first.
- Existing `PUT /admin/api/plans/{id}` has the same pre-authentication empty 403.
  No production plan was changed: probes used no session and a nonexistent ID.
  There is no existing admin PATCH handler to compare; the working write-method
  control is POST below, plus authenticated plan PUT in the fixed local test.
- POST `/admin/api/logout` with no session reaches auth and returns structured
  `401 TOKEN_INVALID` rather than empty 403. POST is allowed by CORS defaults.
- Active Caddy config has no method matchers; this is not a proxy PUT restriction.
- Production `/admin/app.js` was byte-identical to the pre-edit local resource,
  SHA-256 `30156559ff1251cb3c3b701f0bb421e6878e238dee6b514fc93cc87f5fda6edb`.
  There is no stale frontend/backend asset mismatch in this deployment.
- The frontend already sends `credentials: "same-origin"`, JSON Content-Type and
  the session's `X-CSRF-Token` on writes. CSRF is in page memory; the cookie is
  Secure, HttpOnly, SameSite=Strict, Path=/admin. Referer is not an Origin substitute.

These production probes deliberately made no authenticated write. The exact
authenticated GET/PUT/POST comparison was reproduced locally against the deployed
JAR using an isolated database and generated fixture admin, with HTTPS Origin,
HTTP backend, Secure cookie and valid CSRF.

## Minimal fix / unchanged security

- `Application.kt`: scope the existing, unchanged public CORS policy to client API
  routes instead of the whole application.
- `premium/PremiumRoutes.kt`: separate the public/client route registration from
  admin registration so only public APIs inherit that policy. All URLs/DTOs stay
  unchanged. No domain/service logic changed.
- Admin mutations retain their exact configured Origin check, Sec-Fetch-Site
  check, session expiry and constant-time CSRF validation. There is no wildcard
  write-CORS, trusted-forwarded-header change, Referer fallback or insecure-cookie
  workaround. Public CORS methods, origins and allowed headers are not broadened.
- `admin/app.js`: recognize empty/HTML/malformed error responses by HTTP status;
  give useful Persian 403 recovery guidance and distinct CSRF/Origin messages.
  Never display raw response HTML. Non-JSON 401 also invalidates the matching
  current session, but a late 401 cannot invalidate a newer session.
